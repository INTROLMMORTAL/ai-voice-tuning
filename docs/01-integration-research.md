# Этап 1. Интеграция с nekto.me — исследование и архитектурное решение

## Что проверено, а что НЕТ (важно)
В среде, где писался проект, нет доступа в интернет, поэтому **код nekto.me не изучался**. Всё ниже про сайт — гипотезы, которые расширение само проверяет в вашем браузере (см. «Как проверить»). Про сам Chrome сказано то, что известно из документации/поведения платформы.

## Как звук попадает в WebRTC (общая схема)
`navigator.mediaDevices.getUserMedia({audio})` → `MediaStream` → `RTCPeerConnection.addTrack / addTransceiver / replaceTrack` → кодек Opus → сеть.
Чтобы собеседник услышал обработанный голос, **сайт должен отправить именно наш MediaStreamTrack**. Web Audio сам по себе ничего не подменяет: `MediaStreamAudioDestinationNode` даёт новый трек, но сайт о нём не знает, пока мы не вернём его из `getUserMedia`.

## Вариант A (реализован): перехват getUserMedia в MAIN-world
- Content script `world: "MAIN"`, `run_at: document_start` (Chrome ≥ 111) подменяет `MediaDevices.prototype.getUserMedia` до скриптов сайта. Сайт получает `MediaStream` с треком из `MediaStreamAudioDestinationNode`, который питает цепочка AudioWorklet.
- Подмена на прототипе, а не на `navigator.mediaDevices`, чтобы ловить и вызовы через `MediaDevices.prototype.getUserMedia.call(...)`.
- `stop()` обработанного трека останавливает исходный микрофон; `ended` исходного трека пробрасывается; `label` и `getSettings().deviceId` копируются, чтобы логика сайта (выбор устройства) не ломалась.
- **Fail-open**: любая ошибка (AudioContext не запустился, нет базового URL) → сайт получает оригинальный поток. Звук не может пропасть из-за расширения.
- **Watchdog**: если worklet перестал присылать метрики 2.5 с → маршрут `src→dest` напрямую (трек у сайта тот же, обработка отключается).
- **Проверка факта передачи** (`hook.js → poll()`): (1) `RTCRtpSender.track.__avt === true` — сайт держит именно наш трек; (2) уровень из `getStats()` (`media-source.totalAudioEnergy`) сверяется с выходом DSP за тот же интервал (`sendMatchDb`, ≈0 дБ = передаётся наш сигнал); (3) `remote-inbound-rtp` показывает, что пакеты доходят до собеседника. Прослушать, что слышит собеседник, расширение не может — это можно проверить только вторым устройством/другом.

### Известные риски варианта A (проверять в реальности)
| Риск | Что произойдёт | Как расширение реагирует |
|---|---|---|
| Сайт вызывает getUserMedia в iframe/worker | Хук не сработает, трек не обработан | `all_frames: true`; индикатор «сайт отправляет обработанный трек: НЕТ» в popup |
| Сайт получил поток до загрузки расширения (кэш) | Не обработан | то же; перезагрузить вкладку |
| CSP блокирует `addModule` с `chrome-extension://` | Нет worklet | автоматический нативный запас: HPF+EQ+limiter (без gate/de-esser/компрессора), режим показан в popup |
| AudioContext «suspended» (autoplay policy) | Тишина в обработанном треке! | не отдаём трек, fail-open на оригинал |
| Браузерные AEC/NS/AGC | Двойная обработка | по умолчанию — ограничения сайта как есть; опция «без браузерного NS/AGC» включается осознанно (эхоподавление не трогается) |
| Сайт может определить расширение | Фингерпринтинг | `data-avt-base` и web_accessible_resources видны странице; скрытие не делалось намеренно (без обходов) |
| Сайт использует нестандартный путь (WebAudio-захват, `captureStream` и т.п.) | Хук не перехватит | диагностика покажет; тогда нужен вариант B |

## Альтернативы, если A не работает
| | Задержка (оценка, не измерено) | Установка | Надёжность | Совместимость с Windows |
|---|---|---|---|---|
| **A. MAIN-world хук** (этот проект) | +≈3–6 мс (lookahead 1 мс + блок 2.7 мс + буферы контекста) | Загрузить распакованное расширение | Зависит от того, как сайт берёт микрофон; обходится fail-open | Любой Chrome ≥111 |
| **B. Виртуальный кабель (VB-Cable) + десктоп-приложение**, обработка WASAPI→кабель | ≈10–30 мс (двойная буферизация + кабель) | Драйвер третьей стороны, права администратора, настройка устройства в Windows | Высокая: работает для любого сайта/приложения | Windows 10/11 |
| **C. Equalizer APO (системный APO на микрофон) + Peace** | ≈ единицы мс | Установка APO, правка системных настроек — только с согласия | Средняя: конфликты с драйверами/Windows Sonic; нет авто-анализа | Windows |
| **D. Собственный виртуальный аудио-драйвер** | минимальная | Подпись драйвера, сложная разработка | Высокая, но очень дорого | Windows |

**Рекомендация:** начать с A (самый простой и самый быстрый), и только если диагностика покажет `hook-miss`, делать B. Десктоп-приложение для B использует то же `dsp-core.js` (чистый JS, портируется в Electron/Node без изменений).

## Как проверить в реальности (чек-лист)
1. `chrome://extensions` → Режим разработчика → «Загрузить распакованное» → папка проекта.
2. Откройте `https://nekto.me/audiochat`, F12 → Console, фильтр `[AVT]`: должны быть «hook установлен» и после старта поиска «обработанный трек выдан сайту».
3. Popup расширения: «Сайт отправляет обработанный трек: да», «Сверка отправленного уровня» около 0 дБ.
4. Включите «Обход (bypass)» и спросите собеседника/второе устройство, слышна ли разница; затем снимите.
5. Если «НЕТ» или в логе `fail-open`/`worklet недоступен` — пришлите текст логов, это определит, нужен ли вариант B.
